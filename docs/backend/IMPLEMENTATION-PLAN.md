# EnglishCodeApp Backend — End-to-End Implementation Plan

**Status:** Draft execution plan. No task is considered complete without evidence.  
**Source architecture:** [ARCHITECTURE.md](./ARCHITECTURE.md)  
**Current baseline:** `feat/backend-domain-foundation`  
**Working documentation branch:** `docs/backend-architecture-v2`

## Delivery rules

- Work in small, reviewable branches and pull requests.
- Do not merge, deploy, run production migrations, provision paid services, or raise spending limits without explicit approval.
- Keep existing user data and production resources untouched.
- Every task must have acceptance evidence: test output, CI run, migration result, or reviewed diff.
- A file existing is not proof that the feature works.
- Update Notion after material architecture or implementation changes.

## Phase 0 — Repair the existing foundation (P0)

### B0.1 Correct Telegram HMAC verification
- Fix key/message order to match the official Telegram Mini Apps algorithm.
- Add independent known-good test vectors, not generated by the same helper under test.
- Add tests for valid signature, invalid signature, tampered fields, duplicate parameters, expired auth_date, and future skew.
- Acceptance: official vector passes; every mutation/tamper case fails; no bot token or initData appears in logs.

### B0.2 Make replay protection and session issuance atomic
- Inspect current D1 batch semantics and choose a conditional-write design.
- Ensure concurrent identical initData requests result in at most one successful session.
- Remove best-effort revoke as the primary correctness mechanism.
- Acceptance: deterministic D1 integration test proves exactly one winner under concurrency.

### B0.3 Resolve migration history
- Establish whether any shared database has applied migrations 0001–0003.
- If none have been applied outside local tests, consolidate the duplicate replay table definition before first shared use and renumber only before the migration history becomes immutable.
- If any shared DB has applied them, preserve history and add a forward migration; never rewrite applied migrations.
- Acceptance: migrations apply cleanly from empty DB and from the supported previous schema; docs match actual SQL.

### B0.4 Correct answer idempotency and attempt completion
- Define whether duplicate answer requests return the original response or a conflict.
- Require idempotency key or strict same-answer semantics; reject a different answer after first acceptance.
- Implement single-winner completion and atomic progress update.
- Acceptance: concurrency tests prove no post-completion answers and no double progress increments.

### B0.5 Fix request correlation
- Generate an application request ID for every request.
- Preserve Cloudflare Ray ID as a separate diagnostic field.
- Validate any trusted incoming trace ID and never let arbitrary client input become a privileged correlation token.
- Acceptance: response contains app request ID; structured log distinguishes app request ID and Ray ID.

### B0.6 Diagnose and repair CI
- Retrieve failed job logs or reproduce commands locally.
- Run install, frontend/backend typecheck, tests, and frontend build on Node 22.
- Pin dependency installation to the lockfile and use `npm ci` in CI.
- Acceptance: CI green on the exact commit, with logs retained.

## Phase 1 — Identity and access hardening (P1)

### B1.1 Internal identity model
- Add provider-neutral `users` and `user_identities` model.
- Map Telegram user ID as provider subject; do not key application data by mutable username.
- Define account linking and duplicate identity behavior.
- Acceptance: Telegram identity maps to one stable internal user; no duplicate provider subject.

### B1.2 Session lifecycle
- Decide cookie vs Bearer for Telegram WebViews using a recorded ADR.
- Implement expiry, revocation, idle/absolute lifetime, and optional revoke-all sessions.
- Keep token hash only in D1.
- Acceptance: expiry/revocation/reload/background-resume tests pass on target clients.

### B1.3 Abuse controls
- Add rate limits to auth, attempt creation, answer submission, and admin routes.
- Bound body size, query size, pagination, and expensive database operations.
- Acceptance: abuse tests receive predictable 429/4xx responses; legitimate use remains functional.

### B1.4 Origin and browser security
- Prefer same-origin app/API.
- Configure exact allowed origins; no wildcard with credentials.
- Add CSRF protection if cookie auth is chosen.
- Acceptance: allowed Telegram app origin works; untrusted origin is rejected.

## Phase 2 — Stable learning core (P1)

### B2.1 Content and versioning
- Define course, lesson, question, content version, and publish lifecycle.
- Published content is immutable; edits create a new version.
- Attempts pin a content version and scoring policy.
- Acceptance: old attempts remain reproducible after content changes.

### B2.2 Attempt state machine
- Define created/in_progress/completed/expired/abandoned transitions.
- Enforce owner and state in every write query.
- Define retry, expiry, and max-active-attempt rules.
- Acceptance: invalid transitions fail consistently and are covered by tests.

### B2.3 Assessment policy
- Define denominator, unanswered behavior, weighting, normalization, rounding, pass threshold, and retry behavior.
- Store policy version with result.
- Acceptance: deterministic unit tests cover boundary and edge cases.

### B2.4 Progress model
- Define best score vs latest score, completion count, skill-level progress, and mastery criteria.
- Ensure repeated completion does not double count.
- Acceptance: D1 integration tests prove exact progress behavior.

## Phase 3 — Product capabilities (P2, only after core is stable)

### B3.1 Vocabulary and spaced repetition
- Define vocabulary source, user state, review schedule, and algorithm version.
- Schedule review calculations server-side.
- Acceptance: deterministic schedule tests, timezone handling, and idempotent review events.

### B3.2 Four language skills
- Extend content model for reading, listening, writing, speaking without hard-coding all content into one question shape.
- Define skill-specific assessment interfaces and scoring.
- Acceptance: each supported item type has schema, grading policy, and test fixtures.

### B3.3 Gamification and goals
- Add points, streaks, badges, and goals only with clear anti-abuse rules.
- Use immutable reward events or auditable ledger for point changes.
- Acceptance: duplicate requests cannot award points twice.

### B3.4 Administration and content publishing
- Add staff RBAC, audit logs, preview/publish workflow, and rollback by version.
- Acceptance: unauthorized staff actions fail; all publish changes are auditable.

## Phase 4 — Integrations and async work (P2/P3)

### B4.1 Telegram Bot API
- Add webhook validation, secret token, update idempotency, and retry handling.
- Separate inbound webhook from outbound notification service.
- Acceptance: replayed update is processed once; malformed webhook rejected.

### B4.2 Audio and media
- Add private R2 assets, upload constraints, metadata, signed access, and retention.
- Add Queue jobs only for actual asynchronous processing.
- Acceptance: file type/size/duration validation, ownership, job idempotency, and deletion tests pass.

### B4.3 AI/STT/TTS adapters
- Provider-neutral interfaces, bounded timeouts, quotas, retries, and cost tracking.
- User consent and voice-data retention defined before collecting recordings.
- Acceptance: provider outage degrades gracefully; no paid provider activated without approval.

## Phase 5 — Operations and beta readiness (P1 before public beta)

- Local D1 migration harness and isolated preview D1.
- Structured logs, request correlation, metrics, alerts, and runbooks.
- Backup/restore drill and forward-fix migration procedure.
- Data export/deletion and retention implementation.
- Cross-user authorization, abuse, concurrency, and end-to-end tests.
- Telegram client matrix: iOS, Android, Desktop, browser.
- Cost/quota review and graceful degradation.
- Acceptance: all release gates in ARCHITECTURE.md pass and evidence is linked from the PR.

## Definition of done

A phase is complete only when its acceptance criteria pass on the exact commit and the PR links the evidence. “Implemented”, “tested”, “verified”, and “released” are separate states. A planned item is not complete merely because its design is documented.
