# ADR-0001: Cloudflare-native و سیاست Free-first

- **وضعیت:** پذیرفته‌شده به‌عنوان مبنای طراحی
- **تاریخ:** ۲۶ نوامبر ۲۰۲۶
- **دامنه:** ساختار اولیهٔ EnglishCodeApp
- **تأیید هزینه:** هیچ هزینهٔ پولی بدون تأیید صریح مالک مجاز نیست.

## زمینه

محصول از Telegram Bot و Mini App آغاز می‌شود، ولی در آینده باید وب و موبایل را هم پشتیبانی کند. مالک پروژه خواسته است زیرساخت در Cloudflare متمرکز باشد و شروع کار فقط بر امکانات رایگان متکی بماند.

## تصمیم

- TypeScript زبان اصلی.
- React + Vite برای Mini App.
- Cloudflare Workers برای backend.
- Hono به‌عنوان گزینهٔ پایهٔ API، مشروط به PoC سازگاری.
- Cloudflare D1 برای داده‌های رابطه‌ای اولیه.
- Cloudflare R2 برای object/file storage.
- Cloudflare Queues فقط برای jobهای غیرهم‌زمان موردنیاز.
- Workers Static Assets برای فایل‌های فرانت‌اند.
- AI از پشت interface/adapter و فقط بعد از ارزیابی کیفیت و سهمیه.
- Modular Monolith به‌جای microservices در شروع.
- migrationهای SQL مرجع تغییر schema هستند؛ ORM اختیاری و مشروط به آزمون.
- در پروژهٔ جدید، انتخاب CLI و config مطابق راهنمای رسمی جاری Cloudflare انجام می‌شود؛ تا زمانی که ابزار پیکربندی تثبیت نشده، فایل Wrangler به‌صورت پیش‌فرض ایجاد نمی‌شود.

## گزینه‌های ردشده در فاز اول

- Node.js/NestJS به‌عنوان runtime مستقل Production: با هدف استقرار کاملاً Cloudflare-native هم‌راستا نیست.
- PostgreSQL/Redis/pg-boss: سرویس‌های جدا و هزینه/عملیات اضافی ایجاد می‌کنند و در شروع نیاز قطعی نداریم.
- Microservices: پیچیدگی استقرار، مشاهده‌پذیری و ارتباطات را پیش از اثبات نیاز بالا می‌برند.
- Durable Objects، Vectorize، AI Search و دیگر محصولات: تا زمانی که نیاز مشخص و آزمون‌شده نباشد فعال نمی‌شوند.

رد این گزینه‌ها دائمی نیست؛ تغییر تصمیم نیازمند ADR جدید و تحلیل هزینه/فایده است.

## پیامدها

### مثبت
- تعداد سرویس‌ها و عملیات نگهداری در شروع کم می‌ماند.
- دامنه‌ها در کد مرزبندی شده‌اند و در صورت نیاز قابل جداسازی‌اند.
- دادهٔ تراکنشی، فایل و job از نظر نقش تفکیک می‌شوند.
- سیاست عدم ارتقای خودکار هزینه قابل اعمال است.

### منفی و ریسک‌ها
- D1 به سقف‌های اندازه، query و concurrency محدود است.
- سهمیهٔ Free برای رشد نامحدود مناسب نیست.
- APIها و کتابخانه‌ها باید با Workers سازگار باشند.
- محدودیت CPU برای پردازش سنگین و synchronous نامناسب است.
- مهاجرت آینده به چند دیتابیس یا لایهٔ دادهٔ دیگر نیازمند طراحی و آزمون خواهد بود.

## گیت‌های قبل از تثبیت فناوری

1. React/Vite و Workers Static Assets در یک نمونهٔ حداقلی build و اجرا شوند.
2. Hono در runtime انتخاب‌شده با bindingهای موردنیاز کار کند.
3. migration و queryهای D1 در محیط توسعه و محیط آزمایشی تأیید شوند.
4. adapterهای Telegram، R2، Queues و AI تست شوند.
5. بودجه و رفتار quota exhaustion آزمایش شود.

تا زمان عبور از این gateها، انتخاب فناوری «تصمیم معماری پایه» است نه «استک production تأییدشده».
